Openflow: Conector Kafka

Ingestar datos en tiempo real desde un cluster Kafka hacia Snowflake usando el conector nativo de Openflow.

Arquitectura​

Kafka Cluster                    Openflow Runtime              Snowflake
┌──────────────┐                ┌──────────────────┐         ┌────────────┐
│ Topic: txns  │──(consume)────>│ ConsumeKafka     │         │            │
│ Topic: events│                │      │           │         │ RAW schema │
│              │                │      ▼           │         │            │
│ (Brokers)    │                │ Transformations  │──(API)─>│ Destination│
│              │                │      │           │         │ Tables     │
│              │                │      ▼           │         │            │
│ Topic: DLQ   │<──(publish)────│ PublishSnowpipe  │         │ Error      │
│              │                │  Streaming       │         │ Tables     │
└──────────────┘                └──────────────────┘         └────────────┘

Requisitos previos​

  1. Deployment de Openflow activo (BYOC o Snowflake Deployment)
  2. Runtime creado y corriendo
  3. Cluster Kafka accesible desde el runtime
  4. Base de datos y schema destino en Snowflake

Paso 1: Configurar cuenta Snowflake​

Crear rol y usuario dedicado​

USE ROLE SECURITYADMIN;

-- Rol dedicado para el conector
CREATE ROLE IF NOT EXISTS OPENFLOW_KAFKA_ROLE;

-- Permisos sobre el destino
GRANT USAGE ON DATABASE SNOWFLAKE_POC TO ROLE OPENFLOW_KAFKA_ROLE;
GRANT USAGE ON SCHEMA SNOWFLAKE_POC.RAW TO ROLE OPENFLOW_KAFKA_ROLE;

-- OWNERSHIP requerido para ingestar datos
GRANT CREATE TABLE ON SCHEMA SNOWFLAKE_POC.RAW TO ROLE OPENFLOW_KAFKA_ROLE;

-- Warehouse para ingestion
GRANT USAGE, OPERATE ON WAREHOUSE ETL_WH TO ROLE OPENFLOW_KAFKA_ROLE;
Un rol por cluster

Snowflake recomienda crear un rol separado por cada cluster Kafka para mejor control de acceso. Los privilegios deben ser directos (no heredados).

Crear tabla destino​

USE ROLE OPENFLOW_KAFKA_ROLE;

CREATE TABLE SNOWFLAKE_POC.RAW.KAFKA_TRANSACTIONS (
    kafkaMetadata VARIANT
)
ENABLE_SCHEMA_EVOLUTION = TRUE
ERROR_LOGGING = TRUE;
  • ENABLE_SCHEMA_EVOLUTION: Snowflake agrega columnas automaticamente cuando detecta nuevos campos en los mensajes JSON
  • ERROR_LOGGING: Filas que fallan por incompatibilidad de schema se capturan en una error table

Transferir ownership​

USE ROLE SECURITYADMIN;
GRANT OWNERSHIP ON TABLE SNOWFLAKE_POC.RAW.KAFKA_TRANSACTIONS
  TO ROLE OPENFLOW_KAFKA_ROLE;

Paso 2: Instalar el conector​

  1. En Openflow UI: ir a Connector Library
  2. Buscar Kafka y seleccionar Install
  3. Elegir tu runtime
  4. Autenticarse con credenciales de Snowflake

Paso 3: Configurar parametros​

Click derecho en el process group > Parameters:

ParametroValorDescripcion
Kafka Bootstrap Serversbroker1:9092,broker2:9092Lista de brokers
Kafka Consumer Group IDopenflow-ingest-001ID unico del consumer group
Kafka Topicstransactions,eventsTopics separados por coma
Kafka Topic Formatnamesnames para lista, pattern para regex
Kafka Auto Offset ResetearliestDesde donde empezar a leer
Snowflake Destination DatabaseSNOWFLAKE_POCBase de datos destino
Snowflake Destination SchemaRAWSchema destino
Snowflake Destination TableKAFKA_TRANSACTIONSTabla destino

Si Kafka usa autenticacion SASL​

ParametroValor
Kafka SASL UsernameTu username
Kafka SASL PasswordTu password (usar secrets manager)

Secrets manager (recomendado)​

Almacenar credenciales en AWS Secrets Manager y referenciarlas desde Openflow:

  1. Configurar Parameter Provider en Openflow (menu hamburguesa > Controller Settings)
  2. Usar el EC2 instance role del runtime para autenticarse al secrets manager
  3. Referenciar credenciales por path en los parametros del conector

Paso 4: Iniciar el conector​

  1. Click derecho en el canvas > Enable all Controller Services
  2. Click derecho > Start

El conector comienza a consumir mensajes.

Columna KAFKAMETADATA​

Cada fila incluye metadata del mensaje Kafka:

SELECT
    kafkaMetadata:topic::STRING AS kafka_topic,
    kafkaMetadata:partition::NUMBER AS kafka_partition,
    kafkaMetadata:offset::NUMBER AS kafka_offset,
    kafkaMetadata:timestamp::NUMBER AS kafka_timestamp,
    kafkaMetadata:key::STRING AS kafka_key,
    *
FROM SNOWFLAKE_POC.RAW.KAFKA_TRANSACTIONS
LIMIT 10;
CampoTipoDescripcion
topicSTRINGNombre del topic
partitionNUMBERParticion Kafka
offsetNUMBEROffset del mensaje
timestampNUMBERTimestamp de Kafka
keySTRINGKey del mensaje (si existe)
headersOBJECTHeaders del mensaje

Schema evolution automatico​

Con ENABLE_SCHEMA_EVOLUTION = TRUE, cuando llega un mensaje con un campo nuevo:

{
  "order_id": 12345,
  "customer_name": "John",
  "new_field": "value"    // <-- campo nuevo
}

Snowflake automaticamente agrega la columna NEW_FIELD a la tabla. No se requiere ALTER TABLE manual.

Tablas Iceberg como destino​

El conector soporta tablas Iceberg como destino:

CREATE ICEBERG TABLE SNOWFLAKE_POC.RAW.KAFKA_EVENTS_ICEBERG (
    kafkaMetadata OBJECT(
        topic STRING, partition INTEGER,
        offset BIGINT, key STRING,
        headers MAP(STRING, STRING),
        timestamp BIGINT
    ),
    event_id INT,
    event_type STRING,
    payload VARIANT
)
EXTERNAL_VOLUME = 'SNOWFLAKE_MANAGED'
CATALOG = 'SNOWFLAKE'
ICEBERG_VERSION = 3
ENABLE_SCHEMA_EVOLUTION = TRUE;

Medir latencia de ingestion​

Habilitar row timestamps para medir cuando llegan las filas:

ALTER TABLE SNOWFLAKE_POC.RAW.KAFKA_TRANSACTIONS
  SET ROW_TIMESTAMP = TRUE;

-- Consultar latencia
SELECT
    kafkaMetadata:topic::STRING AS topic,
    COUNT(*) AS rows_ingested,
    DATEDIFF('second',
        TO_TIMESTAMP(kafkaMetadata:timestamp::NUMBER / 1000),
        METADATA$ROW_LAST_COMMIT_TIME
    ) AS latency_seconds
FROM SNOWFLAKE_POC.RAW.KAFKA_TRANSACTIONS
WHERE METADATA$ROW_LAST_COMMIT_TIME >= DATEADD('hour', -1, CURRENT_TIMESTAMP())
GROUP BY topic, latency_seconds
ORDER BY latency_seconds DESC;

Error handling​

Errores server-side (Snowflake)​

Con ERROR_LOGGING = TRUE, las filas incompatibles se capturan automaticamente:

-- Ver errores de ingestion
SELECT * FROM TABLE(SNOWFLAKE_POC.RAW.KAFKA_TRANSACTIONS!ERROR_TABLE())
ORDER BY ERROR_TIMESTAMP DESC
LIMIT 20;

Errores client-side (Openflow)​

Configurar un Dead Letter Queue (DLQ) para mensajes que no se pueden parsear:

  1. En el ConsumeKafka processor: desactivar auto-termination de parse failure
  2. Agregar un PublishKafka processor apuntando al topic DLQ
  3. Conectar parse failure al publisher DLQ

Observabilidad​

-- Dashboard de ingestion con Openflow event table
SELECT
    RESOURCE_ATTRIBUTES['snow.openflow.runtime.name']::STRING AS runtime,
    RECORD['severity_text']::STRING AS severity,
    RECORD_ATTRIBUTES['message']::STRING AS message,
    TIMESTAMP
FROM SNOWFLAKE_POC.RAW.OPENFLOW_EVENTS
WHERE TIMESTAMP >= DATEADD('hour', -1, CURRENT_TIMESTAMP())
ORDER BY TIMESTAMP DESC
LIMIT 50;
